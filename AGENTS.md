# Agent Instructions

Read `CLAUDE.md` and `README.md` before making substantial changes. These
instructions apply to the entire repository.

## Protect live X1 state

- Treat X1 mainnet as production. Several checked-in defaults point directly to
  `https://rpc.mainnet.x1.xyz`, including `Anchor.toml`, relay clients, Docker
  Compose, initialization scripts, and the files named `test-mainnet.ts`.
- Do not deploy or upgrade a program, initialize or mutate an on-chain account,
  start a production relay, submit a transaction, fund a wallet, rotate an
  oracle key, or run a mainnet integration script without explicit owner
  approval for that exact action and network. A request to build, test, fix, or
  release code does not imply permission to write to a live network.
- Default automated tests to a local validator or a mocked service. Use only
  ephemeral test accounts created for the current test. Read-only RPC queries
  are allowed when they are necessary to inspect state.

## Protect keys, tokens, and credentials

- Never print, copy, expose, or commit secret-key contents, OpenBao tokens, or
  environment files. Do not read key files merely to identify them; derive and
  display a public key only when the task requires it.
- Treat `oracle-v2-keypair.json` as sensitive deployed-program key material.
  Do not modify, remove, rotate, or use it without explicit owner approval.
- Never use wallets from `~/.config/solana/` or any pre-existing relay key for
  development or testing. The mainnet test scripts reference a pre-existing
  wallet; do not run them by default.
- `relay/openbao-creds.json` is generated by the local demo and contains a root
  token and relay token. It is ignored; never force-add or commit it. Use the
  teardown script to remove demo credentials.
- Keep relay key directories, `.env` files, logs, generated artifacts, and
  local service state out of commits.

## Security changes require explicit approval and hand-testing

- Do not introduce or enable a new authentication, authorization, key
  lifecycle, signing, permission, network restriction, or security-driven user
  flow without the owner's explicit approval of that exact mechanism.
- Before approval, describe the operator workflow, failure modes,
  compatibility impact, and rollback plan. Keep the change isolated and easy
  to review.
- Before a security change is merged or rolled out, it must be hand-tested end
  to end in a representative environment using the supported operator flow.
  Unit tests, mocks, simulations, CI, and code review do not replace that
  hand-test. The owner must confirm the result and approve rollout.

## Repository and change hygiene

- Start by checking the worktree, branch, remotes, and relevant documentation.
  Preserve unrelated user changes and keep one coherent task per branch.
- Never create, modify, disable, or delete GitHub branch protection rules or
  repository/organization rulesets.
- Before committing or pushing, review the relevant diff, stage only intended
  files, and run checks proportional to the change. Never force-push unless the
  owner explicitly requests it for the specific branch.
- Do not credit an agent or assistant in commits, source comments, or project
  documentation.
